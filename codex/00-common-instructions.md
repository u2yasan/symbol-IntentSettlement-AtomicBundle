# Codex 共通作業指示

> 現在の段階（2026-10-26）: 仕様詳細化と雛形作成のみ。以下は将来、実装を依頼された段階の指示であり、今すぐclone・C++実装・ノード起動を行う指示ではない。先に[構成](../docs/repository-layout.md)、[判断一覧](../docs/decisions.md)、[受入表](../docs/acceptance-matrix.md)を読む。

この文書は、IntentSettlementとAtomicBundleのどちらの作業でも最初に読みます。現在のリポジトリの `AGENTS.md`、ビルド規約、ユーザーから与えられた制約を確認したうえで適用してください。

## 1. 依頼の完了条件

設計書に基づき、公式C++ catapultへ新取引型を実装し、対象テストと隔離した私設ネットワークによる受け入れ試験を行ってください。設計説明、疑似コード、HTTPのモック、Pythonの残高モデルだけで完了しないでください。

不足する環境や権限がある場合は、実行可能な作業を進め、未実施部分・理由・必要な手順を具体的に記録します。試験結果を捏造せず、単体試験の成功をネットワーク検証の成功と表現しないでください。

## 2. 開始時の確認

1. `README.md`、`docs/00-common-spec.md`、対象案の設計書と指示書を読む。
2. 実装先リポジトリを確認する。存在しなければ公式 `https://github.com/symbol/symbol` から隔離したローカル作業コピーを用意する。
3. gitの現在のブランチ・コミット・未コミット変更と、適用される `AGENTS.md` を確認する。既存作業を上書きしない。
4. 基準は `6c04695555230c89a6ffa2ac4d41774dcac77ae3`。異なるコミットへ実装する場合は差分とAPI変更を先に記録し、黙って基準を変えない。
5. Intentは `poc/intent-settlement-v1`、Atomicは `poc/atomic-bundle-v1` を候補に、別作業ツリーを使う。既存名があれば衝突しない名前を選び、記録する。
6. ビルド手順・CMake構成・ネイティブテスト配置・nemgenとプラグインの読み込み方を実ソースから確認する。コマンドや既存APIを推測で作らない。

## 3. 作業の進め方

- M0から順に進め、各段階で具体的なファイルと検証結果を残す。通常の実装判断ごとにユーザーへ確認を要求しない。
- リポジトリ内の検索は `rg` を優先する。依存のない調査や読み取りを並行し、同じファイルへの編集を競合させない。
- 設計の安全性条件を緩める代替実装は禁止する。実在APIと文書案が合わない場合は、機能を保った最小変更を行い、Architecture Decision Recordに根拠を記録する。
- マルチシグやモザイク制限に対応しきれなければ、v1の範囲に従って明示的な失敗にする。黙って検査を省かない。
- 広範なリファクタリングや、関係のない依存更新を混ぜない。
- CLI引数やログへ実用秘密鍵を露出させない。fixture鍵は公開済みの使い捨てテスト専用と明記する。
- ネットワークアクセスはソース取得・依存取得と隔離テストに限定する。公開チェーンへ取引を送信しない。

## 4. 実装前に固定するもの

次を `docs/poc/<案名>/protocol-abi.md` に記録してください。配置はリポジトリ規約に合わせて変更できますが、参照を更新します。

- 取引型、版、FacilityCode、キャッシュ番号。予約値との衝突検査結果。
- 固定・可変バイト列のレイアウト、endianness、padding、署名対象、hash、全長上限。
- 合意設定、有効化条件、genesis作成条件、既存機能から変える箇所。
- 外側feeの通知順。共通仕様に従い、PoCの全実行高さでCustom処理の後にfeeが引かれる設定と実際の順序を確認する。
- 手数料、DeepCount、receipt source、署名検証コストの扱い。
- 失敗コードと、どの検査で拒否するか。

型名や関数名は「新しく作るもの」と「既存の呼び出し先」を区別します。既存のコアAPIでない名前を、実在するかのように呼び出すコードを残さないでください。

## 5. 検証の方針

最初に対象コンポーネントのテストを実行し、その後に関連する既存のAggregate・Transfer・HashCache・restriction・rollbackの回帰試験を行います。対象が通っただけで終了せず、設計書の各必須受け入れ項目を根拠付きで埋めます。一方、残ったリスクや必須ゲートに関係しないテストの拡大は避けます。

私設ネットワーク試験では、全ノードの同一高さを比較します。時刻が異なる任意の先端同士を比較して一致したと扱わないでください。fork試験は、ブロックを実際に作成・伝播して巻き戻しを起こします。単にobserverのRollbackを呼ぶ単体試験は、別の検証項目です。

新Merkleキャッシュを持つIntentでは、nemgenとノードに同じプラグインを読み込ませます。既存mainnetのgenesis・snapshotへキャッシュを追加する方法は、このPoCの代替になりません。

## 6. 残すべき成果物

各案について、少なくとも次を残してください。

| 成果物 | 内容 |
| --- | --- |
| 実装 | C++ plugin、model、notifications、validators、observers、必要なcacheと設定 |
| クライアント | 注文作成・署名、取引構築、送信、結果確認の最小CLI |
| スキーマ | catbuffer／正規codec、署名・hash・サイズの固定ベクトル |
| 私設ネット構成 | fresh genesis、3ノード設定、起動・停止・データ初期化・再現手順 |
| テスト | 正常系、改ざん、権限、重複、fee、undo、fork、再起動 |
| 証拠 | コミット、設定hash、raw payload、期待値、実測値、block/state/receipt hash、ログ |
| 報告 | 実装済み／実行済み／未実施、残る課題、変更理由、再現コマンド |

証拠の既定配置は `artifacts/poc/<案名>/` とします。大量ログ・秘密鍵・ビルド出力を無差別にgitへ追加しません。再現に必要な小さい公開テストfixtureとサマリーを選別します。

## 7. 最終報告の書式

次の順で報告してください。

1. どの機能が動き、どの必須条件がまだ満たされていないか。
2. 対象コミット、作業ブランチ、主要変更ファイル。
3. 各受け入れテストIDと `PASS / FAIL / NOT_RUN`、証拠へのリンク。
4. 3ノード・fork・再起動の結果。実行していなければ明確に記す。
5. 設計書からの変更と理由。
6. 同じ環境で再現するための正確なコマンド。

この依頼はローカルPoCの実装と検証です。リモートへのpush、PR公開、mainnetへの配置、実資産を使った運用開始は含みません。
